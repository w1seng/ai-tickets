# AI-обробка звернень

Внутрішній інструмент служби підтримки інтернет-магазину. Оператор додає звернення клієнта, а Claude одним кліком визначає його **пріоритет** і **категорію**, пише **короткий підсумок** і готує **чернетку відповіді** клієнту. Результат зберігається в базі й одразу показується на картці звернення.


## Можливості

- Форма «Ім’я клієнта + текст звернення» з валідацією (помилки під полями, введені дані не губляться).
- Список звернень, нові зверху; дані зберігаються в Postgres.
- Кнопка «✨ Аналізувати (AI)» на кожній картці: пріоритет (`low` / `medium` / `high`), одна з [10 категорій](#категорії-звернень), підсумок в одне речення, чернетка відповіді.
- Чернетка пишеться мовою звернення, звертається до клієнта на ім’я (для української — у кличному відмінку) і не вигадує фактів: невідомі дані замінюються плейсхолдерами на кшталт `[номер замовлення]`.
- Кнопка «Копіювати» для чернетки, світла й темна теми, адаптивна верстка, доступність (label-и, focus-ring, `aria-live`).
- Прості обмеження від зловживань: не частіше одного аналізу на 10 секунд для звернення і не більше 200 звернень у базі.

## Стек і чому саме він

| Технологія | Навіщо |
|---|---|
| **Next.js (App Router) + TypeScript (strict)** | Один проєкт для UI і серверної логіки; серверні компоненти читають БД напряму, без окремого API. |
| **Server Actions** | Мутації (`createTicket`, `analyzeTicket`) без ручних API-роутів; секрети не потрапляють у браузер. |
| **Tailwind CSS** | Швидка й послідовна верстка без UI-бібліотек; темна тема через `dark:` + `prefers-color-scheme`. |
| **Neon Postgres + Drizzle ORM** (`neon-http`) | Serverless Postgres, який добре працює на Vercel; Drizzle дає типобезпечні запити й схему в коді. |
| **@anthropic-ai/sdk** | Офіційний SDK Claude з типами, тайм-аутами, повторами й типізованими помилками. |
| **Zod** | Одна бібліотека для валідації і форми, і відповіді моделі. |

## Як влаштований AI-аналіз

Код — у [`src/lib/analyze.ts`](src/lib/analyze.ts), виклик — у Server Action `analyzeTicket` ([`src/app/actions.ts`](src/app/actions.ts)).

1. **Tool use з примусовим викликом.** Моделі передається один інструмент `save_analysis` з JSON Schema (`priority` і `category` — enum, `summary` і `draftReply` — рядки з детальними описами) і `tool_choice: { type: "tool", name: "save_analysis" }`. Модель не може відповісти вільним текстом — вона зобов’язана «викликати» інструмент, тож відповідь завжди приходить як **структурований JSON** у блоці `tool_use`.
2. **Zod-валідація.** Вміст `tool_use.input` перевіряється Zod-схемою. Якщо блоку немає, відповідь обрізана за лімітом токенів або дані не відповідають схемі — кидається зрозуміла помилка, і в базу нічого не пишеться.
3. **Збереження в БД.** Валідний результат записується в рядок звернення разом з `analyzed_at = now()`, сторінка оновлюється через `revalidatePath('/')`.
4. **Обробка помилок.** `analyzeTicket` нічого не кидає в UI: помилка логується на сервері (`console.error`), а користувач бачить зрозуміле повідомлення українською залежно від типу (тайм-аут, ліміт запитів, ключ API, збій сервісу, невалідна відповідь).

**Захист від prompt injection.** Текст звернення передається в user-повідомленні всередині тегів `<ticket>…</ticket>`, а системний промпт прямо каже, що це дані від клієнта, а не інструкції: будь-які команди всередині (змінити роль, поставити певний пріоритет, написати щось інше) ігноруються. Додатково вихід обмежений схемою інструмента, тож навіть «успішна» ін’єкція не може змінити формат результату.

Модель задається змінною `ANTHROPIC_MODEL` (за замовчуванням `claude-sonnet-5`), тайм-аут запиту — 30 с, `max_tokens` — 1024.

**Чому Sonnet 5, а не Haiku 4.5.** Обидві моделі проганялися на однаковому наборі тестових звернень (`npm run test:ai`). Пріоритети обидві визначають однаково добре, але чернетки йдуть клієнтам, тому вирішальною була якість мови:

| | Haiku 4.5 | Sonnet 5 |
|---|---|---|
| Мовні помилки на 8 чернетках | 9 (зламані речення, неправильний рід, русизми, кальки, кличний відмінок) | 0 |
| Дотримання правил (без обіцянок, ім’я в кличному відмінку) | порушення в окремих чернетках | без порушень |
| Час відповіді | 2,5–4,5 с | 3,5–7 с |
| Вартість одного аналізу | ≈ $0,004 | ≈ $0,008 |

Подвійна вартість — менше центу за аналіз, а чернетки Sonnet 5 готові до надсилання без правок. Haiku можна повернути без зміни коду: `ANTHROPIC_MODEL=claude-haiku-4-5-20251001`.

## Категорії звернень

ТЗ наводить категорії лише як приклад, тому набір розширено до близького до реальної служби підтримки:

| Ключ | Назва в інтерфейсі | Що сюди потрапляє |
|---|---|---|
| `payment` | Оплата | Списання без замовлення, подвійне списання, помилки оплати, рахунки, розстрочка |
| `refund` | Повернення та обмін | Клієнт хоче повернути товар або гроші, обміняти розмір чи модель |
| `delivery` | Доставка | Терміни, трекінг, адреса, посилка не прийшла, кур’єр не приїхав |
| `order` | Замовлення | Статус, зміна чи скасування замовлення, оплачене, але не відправлене, неповна комплектація |
| `product` | Товар | Брак, пошкодження, невідповідність опису чи фото |
| `technical` | Технічна проблема | Сайт, додаток, вхід в акаунт, пароль, помилки, «все лагає» |
| `complaint` | Скарга на сервіс | Грубість персоналу чи кур’єра, ігнорування, довге очікування відповіді |
| `question` | Консультація | Наявність, характеристики, програма лояльності, способи оплати й доставки |
| `feedback` | Відгук / пропозиція | Подяки, ідеї, побажання |
| `other` | Інше | Усе, що не підходить нікуди |

**Головний принцип: категорія визначається тим, що клієнт хоче, щоб ми зробили, а не темою звернення.** Одна й та сама розбита чашка може бути різними категоріями:

| Звернення | Категорія | Чому |
|---|---|---|
| «Прийшла розбита чашка, поверніть гроші» | `refund` | Клієнт хоче повернення коштів |
| «Прийшла розбита чашка, що робити?» | `product` | Клієнт повідомляє про брак і чекає поради |
| «Оплатила, а замовлення не створилось» | `payment` | Збій самої оплати |
| «Оплатила, замовлення є, але не відправлене» | `order` | Проблема з виконанням наявного замовлення |
| «Кур’єр нагрубив» / «Кур’єр не приїхав» | `complaint` / `delivery` | Поведінка людини vs. сама доставка |
| «Не можу оплатити, сайт видає помилку» | `technical` | Заважає збій сайту, а не оплата |
| «Це вже третє звернення, мені ніхто не відповідає» | `complaint` | Повторне ігнорування — скарга на сервіс, навіть якщо початкова проблема інша |

Ці правила описані в системному промпті, а кожна категорія має опис і в `input_schema` інструмента. Пріоритет визначається окремо; додатково `question` і `feedback` зазвичай отримують `low`, а `complaint` — щонайменше `medium`. `npm run test:ai` перевіряє категорії на 20 зверненнях (по прикладу на кожну категорію плюс спірні випадки) і друкує кількість збігів та список розбіжностей.

На бейджі показується українська назва категорії нейтральним сірим тегом — кольором виділяється лише пріоритет.

## Модель даних

Одна таблиця `tickets` ([`src/db/schema.ts`](src/db/schema.ts)):

| Колонка | Тип | Опис |
|---|---|---|
| `id` | `serial`, PK | Ідентифікатор |
| `customer_name` | `text`, not null | Ім’я клієнта |
| `message` | `text`, not null | Текст звернення |
| `created_at` | `timestamp`, default `now()` | Час створення |
| `priority` | enum `low \| medium \| high`, nullable | Пріоритет (після аналізу) |
| `category` | enum з 10 значень ([див. нижче](#категорії-звернень)), nullable | Категорія (після аналізу) |
| `summary` | `text`, nullable | Підсумок в одне речення |
| `draft_reply` | `text`, nullable | Чернетка відповіді клієнту |
| `analyzed_at` | `timestamp`, nullable | Час останнього аналізу |

## Запуск локально

Потрібні Node.js 20+ (перевірено на 24), база [Neon](https://neon.tech) і ключ [Anthropic API](https://console.anthropic.com).

```bash
# 1. Залежності
npm install

# 2. Змінні оточення: скопіюйте приклад і заповніть DATABASE_URL та ANTHROPIC_API_KEY
cp .env.example .env.local

# 3. Створіть таблицю в базі
npm run db:push

# 4. Запустіть застосунок → http://localhost:3000
npm run dev
```

Інші скрипти:

| Скрипт | Що робить |
|---|---|
| `npm run build` / `npm start` | Продакшн-збірка і запуск |
| `npm run lint` / `npm run typecheck` | ESLint і перевірка типів |
| `npm run test:ai` | Проганяє AI-аналіз на 20 тестових зверненнях (кожна категорія, спірні випадки, сленг, англійською), друкує результати, кількість збігів категорій і розбіжності. Модель можна змінити без правки коду: `ANTHROPIC_MODEL=claude-sonnet-5 npm run test:ai` |
| `npm run db:studio` | Drizzle Studio для перегляду даних |

Секрети (`DATABASE_URL`, `ANTHROPIC_API_KEY`) використовуються лише на сервері; `.env*` (крім `.env.example`) не потрапляють у git.

## Що б покращив далі

- **Автентифікація операторів** — зараз інструмент відкритий для всіх, хто має посилання.
- **Фільтри та пошук** за пріоритетом, категорією, статусом аналізу.
- **Історія аналізів** — окрема таблиця замість перезапису полів, щоб бачити попередні версії й порівнювати моделі.
- **Стрімінг відповіді** — показувати чернетку по мірі генерації замість очікування повного результату.
- **Тести** — юніт-тести валідації й промпту (eval-набір звернень з очікуваними пріоритетами/категоріями), e2e-тести форми.
